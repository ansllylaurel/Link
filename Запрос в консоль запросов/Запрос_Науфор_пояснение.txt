================================================================================
ПОЯСНЕНИЕ К ЗАПРОСУ "Запрос_Науфор.txt"
================================================================================

Исходный материал:
  * "пример для Науфор.xml" - целевая структура колонок (4 раздела:
    Сделки, Сделки РЕПО, МНО, Депозитные вклады).
  * "_ОтчетУправляющегоФорма482/Ext/ObjectModule.bsl" - источник всей
    логики и текстов исходных запросов. Все ссылки на строки ниже
    относятся к этому файлу.

Главный принцип: ничего не выдумывалось - все поля и выражения взяты
из модуля 482. Дополнительно вычислены только два столбца, отсутствующие
в исходном запросе по сделкам (КомиссииБиржи, КомиссииБрокера) - они
заимствованы дословно из соседнего запроса по СВОПам.


================================================================================
1. ПАРАМЕТРЫ ЗАПРОСА
================================================================================

В консоли запросов задаются вручную:

  &Организация       Тип: СправочникСсылка.Организации
  &НачалоПериода     Тип: Дата (00:00:00 первого дня периода)
  &КонецПериода      Тип: Дата (23:59:59 последнего дня периода)
  &СписокКлиентов    Тип: Массив СправочникСсылка.ЮрФизЛица    (можно пустой)
  &СписокСчетовДУ    Тип: Массив СправочникСсылка.СчетаДоверительногоУправления
                                                               (можно пустой)

Логика отбора счетов ДУ "ИЛИ" - можно использовать только один из
двух списков. Если оба пусты, запрос вернёт пустые таблицы (это
страховка от случайного запуска без фильтра).


================================================================================
2. ВТ "_СчетаДУ" - КЛЮЧЕВАЯ ВТ
================================================================================

Источник:
  * Справочник.СчетаДоверительногоУправления (поля Ссылка, Организация);
  * Срез последних РегистрСведений.КлиентыДоверительногоУправления
    на &КонецПериода (поле Клиент).

В модуле 482 эта логика разбита на две ветки (см. функцию
ПолучитьСчетаДоверительногоУправления, стр. 2383-2446):
  * если &КлиентДоверительногоУправления это счёт ДУ - отбор прямой;
  * если ЮрФизЛицо - срез регистра КлиентыДоверительногоУправления.

В нашем запросе обе ветки объединены условием "ИЛИ":

  ГДЕ СчетаДУ.Организация = &Организация
      И (СчетаДУ.Ссылка В (&СписокСчетовДУ)
              ИЛИ КлиентыДУСрезПоследних.Клиент В (&СписокКлиентов))

Колонка Клиент типизирована через
  ВЫРАЗИТЬ(КлиентыДУСрезПоследних.Клиент КАК Справочник.ЮрФизЛица),
потому что DefinedType "КлиентыДоверительногоУправления" может быть
составным, а нам нужно соединение с РеквизитыЮридическихЛиц по
полю ЮрФизЛицо.


================================================================================
3. ВТ "Сделки"
================================================================================

Источник: РегистрСведений.УсловияСделок
  Базовый текст: ВывестиСделки (стр. 1287-1355).

Соответствие колонок XML <-> выражение в запросе <-> строка модуля 482:

  Наименование клиента
    -> ЕСТЬNULL(РеквизитыКлиента.КраткоеНаименованиеПоУставу,
                 ПРЕДСТАВЛЕНИЕ(_СчетаДУ.Клиент))
    Получаем через срез РегистрСведений.РеквизитыЮридическихЛиц с
    фильтром Подразделение = ГруппаКомпаний, Язык = Русский (приём
    взят из ВывестиСделкиДепозитнымВкладам, стр. 1971-1974, и
    ВывестиСделкиПоМНО, стр. 2013-2016).

  Номер договора ДУ
    -> _СчетаДУ.СчетДоверительногоУправления.НомерДоговора
    Реквизит справочника СчетаДоверительногоУправления (см.
    Catalogs/СчетаДоверительногоУправления.xml: атрибут "НомерДоговора",
    тип строка(70), индексируется).

  Наименование эмитента
    -> ЕСТЬNULL(РеквизитыЭмитента.КраткоеНаименованиеПоУставу, fallback)
    Логика взята из функции ПолучитьРеквизитыФинВложения
    (стр. 3194-3277). Эмитент извлекается через
      ЦеннаяБумага.Эмитент.ЮрФизЛицо  (Акции, Облигации, ДепРасписки),
      ЦеннаяБумага.ПаевойИнвестиционныйФонд (Паи)
    и далее через срез РеквизитыЮридическихЛиц
    (стр. 3257-3260). ВЫРАЗИТЬ по каждому типу ЦБ - необходим, т.к.
    у Регистр.УсловияСделок.ЦеннаяБумага составной тип.

  Номер государственной регистрации / ISIN  (колонка XML "НомерГосРегИлиISIN")
    -> ВЫБОР ... ГосударственныйРегистрационныйНомер / РегистрационныйНомер
       ИНАЧЕ ISIN из РегистрСведений.КодыВТорговыхСистемах.СрезПоследних
       (фильтр ВидКода = ISIN).
    Логика - стр. 3266-3273 (модуль читает ISIN через срез
    КодыВТорговыхСистемах). В консольной версии вынесены отдельно
    "НомерГосРег" и "ISIN" + объединённая "НомерГосРегИлиISIN" -
    последняя точно соответствует XML.

  Вид ценной бумаги
    -> ВЫБОР по ССЫЛКА Справочник.Акции/Облигации/Паи/ДепозитарныеРасписки
       -> "Акция"/"Облигация"/"Пай"/"Депозитарная расписка".
    Базируется на ветках ИначеЕсли ТипЗнч(ФинВложение) в
    ПолучитьРеквизитыФинВложения (стр. 3200-3251).

  Дата
    -> УсловияСделок.Период  (стр. 1293).

  Вид сделки
    -> УсловияСделок.Сделка.ВидСделки  (стр. 1301).

  Место заключения
    -> УсловияСделок.Сделка.МестоХранения  (стр. 1302; в модуле
        присутствует под алиасом "МестоЗаключенияСделки").

  Кол-во ЦБ
    -> УсловияСделок.Количество  (стр. 1305).

  Валюта номинала
    -> ВЫБОР ВЫРАЗИТЬ(...).ВалютаНоминала (Акции/Облигации/Паи).
    Реквизит ВалютаНоминала есть у Справочник.Акции, Облигации, Паи
    (см. ссылки на стр. 942, 3203, 3211, 3226).

  Номинал
    -> Акции/Паи: ЦеннаяБумага.Номинал;
       Облигации: РегистрСведений.НоминалыЦенныхБумаг.СрезПоследних
                  (так это делает модуль, стр. 3213-3217).

  Валюта сделки
    -> УсловияСделок.Сделка.ВалютаСделки  (стр. 1303).

  Цена одной ЦБ
    -> УсловияСделок.Цена  (стр. 1308).

  НКД одной ЦБ
    -> ВЫБОР КОГДА ЦеннаяБумага ССЫЛКА Справочник.Облигации
              ТОГДА УсловияСделок.ЦенаКупона  (стр. 1311).

  Сумма сделки в валюте заключения с учётом НКД
    -> УсловияСделок.Сумма + УсловияСделок.СуммаКупона
    Идентично выражению "СуммаВсего" из модуля (стр. 1318).

  Валюта расчётов
    -> УсловияСделок.ВалютаОплаты  (стр. 1304).

  Дата оплаты
    -> УсловияСделок.ДатаОплаты  (стр. 1306).

  Дата перехода прав на ЦБ
    -> УсловияСделок.ДатаПоставки  (стр. 1307).

  Комиссии биржи  *** ДОБАВЛЕННЫЙ СТОЛБЕЦ ***
    -> Подзапрос-агрегация по РегистрНакопления.ЗадолженностиПоДенежнымСредствам
       с фильтрами:
           Период МЕЖДУ &НачалоПериода И &КонецПериода
           ВидЗадолженности = ПоТорговойКомиссии
           ВидДвижения = Приход
           Организация = &Организация
       и соединение по Регистратор = УсловияСделок.Регистратор.
    Модель полностью взята из ВывестиСвопы (стр. 1864-1880).

  Комиссии брокера  *** ДОБАВЛЕННЫЙ СТОЛБЕЦ ***
    -> Подзапрос через Документ.НачислениеЗадолженности.Основания,
       соединённый с РегистрНакопления.ЗадолженностиПоДенежнымСредствам
       по Регистратор = НачислениеЗадолженности.Ссылка,
       с фильтрами:
           ВидЗадолженности = ПоБрокерскойКомиссии
           ВидДвижения = Приход
           Организация = &Организация
           Период МЕЖДУ &НачалоПериода И &КонецПериода
       и соединение по Основание = УсловияСделок.Сделка.
    Модель взята из ВывестиСвопы (стр. 1881-1897).

ФИЛЬТРЫ ЗАПРОСА (как в исходном):
    УсловияСделок.Период МЕЖДУ &НачалоПериода И &КонецПериода
    УсловияСделок.Организация = &Организация
    НЕ УсловияСделок.Отменено
  + ВНУТРЕННЕЕ СОЕДИНЕНИЕ с _СчетаДУ - аналог "СчетДоверительногоУправления В _СчетаДУ"
    из стр. 1338-1342.


================================================================================
4. ВТ "СделкиРЕПО"
================================================================================

Источник: РегистрСведений.УсловияСделокРЕПО.
  Базовый текст: ВывестиСделкиРЕПО (стр. 1357-1704). Это сложный
  каскад из 5 промежуточных временных таблиц - он СОХРАНЁН ПОЛНОСТЬЮ
  и переименован с префиксом "_РЕПО_" чтобы не конфликтовать с
  остальной частью пакета:

      РегистрСведений.УсловияСделокРЕПО
              |
              v
      _РЕПО_ВсеЗаписиБезПериода      (= _ВсеЗаписиБезПериода, стр. 1367)
      _РЕПО_ВсеЗаписи                (= _ВсеЗаписи,           стр. 1397)
      _РЕПО_СделкиПервойЧасти        (= _СделкиПервойЧасти,   стр. 1432)
      _РЕПО_СделкиВторойЧасти        (= _СделкиВторойЧасти,   стр. 1499)
      _РЕПО_ТаблицаДвижений          (= _ТаблицаДвижений,     стр. 1568)
              |
              v
      ВТ "СделкиРЕПО"  (финальный SELECT, стр. 1593-1689).

Параметр &Период из исходного модуля (используется в МИНИМУМ ЕСТЬNULL
на стр. 1396 как "следующий период по умолчанию") заменён на
ДОБАВИТЬКДАТЕ(&КонецПериода, СЕКУНДА, 1) - так мы не вводим лишний
6-й параметр для консоли.

В финальный SELECT добавлены и переименованы поля для XML:

  Наименование клиента, Номер договора ДУ, Эмитент, Номер гос. рег / ISIN,
  Вид ЦБ, Валюта номинала, Номинал
    -> по той же логике, что и для блока "Сделки".

  Дата
    -> _РЕПО_ТаблицаДвижений.Период

  Вид сделки
    -> _ТаблицаДвижений.СделкаРЕПО.ВидСделки  (стр. 1605).

  Место заключения
    -> _ТаблицаДвижений.СделкаРЕПО.МестоХранения  (стр. 1606).

  Кол-во ЦБ
    -> УсловияСделокРЕПО1.Количество  (стр. 1609).

  Валюта сделки
    -> _ТаблицаДвижений.СделкаРЕПО.ВалютаСделки  (стр. 1607).

  Ставка РЕПО
    -> УсловияСделокРЕПО2.СтавкаРЕПО  (стр. 1612).

  Цена / НКД / Сумма с НКД по 1-й части
    -> УсловияСделокРЕПО1.Цена / ЦенаКупона / Сумма + СуммаКупона
       (стр. 1613, 1617, 1623).

  Валюта расчётов
    -> УсловияСделокРЕПО1.ВалютаОплаты  (стр. 1608).

  Дата оплаты по 1-й части
    -> УсловияСделокРЕПО1.ДатаОплаты   (стр. 1610).

  Дата перехода прав по 1-й части
    -> УсловияСделокРЕПО1.ДатаПоставки (стр. 1611).

  Цена / НКД / Сумма с НКД по 2-й части
    -> УсловияСделокРЕПО2.Цена / ЦенаКупона / Сумма + СуммаКупона
       (стр. 1627, 1631, 1637).

  Дата оплаты по 2-й части
    -> УсловияСделокРЕПО2.ДатаОплаты   (стр. 1625).

  Дата перерегистрации по 2-й части
    -> УсловияСделокРЕПО2.ДатаПоставки (стр. 1626).

  Сделка / изменение  (колонка XML "Сделка / изменение")
    -> ВЫБОР:
         если Регистратор - ИзменениеУсловийСделки и совпадает с
            РегистраторПервойЧасти   -> "Изменение 1-й части"
         если Регистратор - ИзменениеУсловийСделки и совпадает с
            РегистраторВторойЧасти   -> "Изменение 2-й части"
         если просто Регистратор - ИзменениеУсловийСделки -> "Изменение"
         ИНАЧЕ                                            -> "Сделка"
       Базовая логика - модуль, стр. 1641-1653 (ЭтоИзменениеСделки +
       НомерИзмененияЧасти).

  Комиссии биржи  *** ДОБАВЛЕННЫЙ СТОЛБЕЦ ***
  Комиссии брокера *** ДОБАВЛЕННЫЙ СТОЛБЕЦ ***
    -> Логика идентична блоку "Сделки", только Регистратор/Основание
       сопоставляются с _ТаблицаДвижений.Регистратор и
       _ТаблицаДвижений.СделкаРЕПО.


================================================================================
5. ВТ "МНО"
================================================================================

Источник: РегистрНакопления.ДенежныеСредстваМНО.
  Базовый текст: ВывестиСделкиПоМНО (стр. 1994-2050).

Соответствие колонок XML:

  Наименование клиента, Номер договора ДУ
    -> Добавлены по той же модели, что и для Сделок: соединение
       с _СчетаДУ и срезом РеквизитыЮридическихЛиц.

  Дата операции
    -> ДенежныеСредстваМНО.Период  (стр. 1999).

  МНО (4 ячейки merge "Информация о МНО")
    -> ТЕКСТОВОЕ ПРЕДСТАВЛЕНИЕ по упрощённой логике функции
       ПредставлениеМНО (ObjectModule.bsl: стр. 3466-3508).

       ВАЖНОЕ ОГРАНИЧЕНИЕ ЯЗЫКА ЗАПРОСОВ 1С:
         * В языке запросов НЕТ функции ФОРМАТ() - это функция
           глобального контекста БСЛ, недоступная в SQL-подобном
           синтаксисе запросов.
         * В языке запросов НЕТ способа корректно сконвертировать
           значение типа Дата или Число в Строку (никакого аналога
           СТРОКА() или ВЫРАЗИТЬ(... КАК СТРОКА(N)) для не-строковых
           типов нет).
         * Соответственно, склеить дату внутрь строки прямо в запросе
           НЕВОЗМОЖНО. Любые попытки конкатенации Дата + " " валятся
           с ошибкой типов на этапе подготовки SQL.

       РЕШЕНИЕ:
         В строковую колонку МНО попадают только текстовые куски:
           "Договор МНО {НомерДоговора}"
                                          либо
           "Договор банк. обслуживания {НомерДоговора}"
                                          +
           ", подтверждение {Номер}"     (если запись в НомераМНО есть)

         А даты вынесены отдельными колонками типа Дата:
           ДатаДоговора       - ДатаЗаключения соответствующего договора
                                (ДоговорМНО или Договор банк. обслуживания).
                                Если оба пусты - возвращается
                                ДАТАВРЕМЯ(1, 1, 1) (пустая дата 1С).
           ДатаПодтверждения  - ДенежныеСредстваМНО.МНО.Дата
                                (см. стр. 3473 модуля -
                                "МНО.Дата КАК ДатаПодтверждения").

         Если на стороне БСЛ нужно собрать строку точно как в
         оригинальном ПредставлениеМНО, это делается ОДНОЙ строкой:
           ПредставлениеМНО =
               Выборка.МНО
               + ?(ЗначениеЗаполнено(Выборка.ДатаДоговора),
                   " от " + Формат(Выборка.ДатаДоговора, "ДФ=dd.MM.yyyy"),
                   "")
               + ?(ЗначениеЗаполнено(Выборка.ДатаПодтверждения),
                   " от " + Формат(Выборка.ДатаПодтверждения, "ДФ=dd.MM.yyyy"),
                   "");

       ЛИДИРУЮЩИЕ НУЛИ в номере подтверждения:
         В БСЛ оригинале (стр. 3501) применяется функция
         РаботаСоСтрокамиКлиентСервер.СократитьЛидирующиеНули(Номер).
         В языке запросов 1С такой функции нет, и каскад из 11 ВЫБОР
         с ПОДСТРОКА - откровенная хрень. Поэтому в запросе номер
         выводится КАК ЕСТЬ (с лидирующими нулями, как лежит в
         РегистрСведений.НомераОбъектов.Номер). При необходимости
         сокращение нулей выполняется БСЛ-кодом после запроса:
           СократитьЛидирующиеНули(СтрокаНомера).

       LEFT JOIN с РегистрСведений.НомераОбъектов (НомераМНО):
         НомераМНО.Организация              = ДенежныеСредстваМНО.Организация
         НомераМНО.СчетДоверительногоУправления = ДенежныеСредстваМНО.СчетДоверительногоУправления
         НомераМНО.Объект                   = ДенежныеСредстваМНО.МНО.Основание
         НомераМНО.Год                      = ГОД(ДенежныеСредстваМНО.МНО.Дата)
         НомераМНО.ВидНумерации             = РаспоряженияНаМНО
       Точная копия ON-условия из БСЛ-функции (стр. 3480-3485).

       Логика выбора (как в модуле, стр. 3492-3502):
         * Если ДоговорМНО заполнен  -> "Договор МНО {НомерДоговора}";
         * иначе если Договор банк.  -> "Договор банк. обслуживания {НомерДоговора}";
         * иначе строка остаётся пустой.
         * К полученной строке добавляется ", подтверждение {Номер}"
           только если НомераМНО.Номер найден (не NULL и не пустой).

       КОНКРЕТНОЕ ВЫРАЖЕНИЕ В ЗАПРОСЕ:
         ВЫБОР
             КОГДА МНО.РасчетныйСчет.ДоговорМНО <> ЗНАЧЕНИЕ(...ПустаяСсылка)
                 ТОГДА "Договор МНО " + ...ДоговорМНО.НомерДоговора
             КОГДА МНО.РасчетныйСчет.Договор   <> ЗНАЧЕНИЕ(...ПустаяСсылка)
                 ТОГДА "Договор банк. обслуживания " + ...Договор.НомерДоговора
             ИНАЧЕ ""
         КОНЕЦ
         + ВЫБОР
             КОГДА ЕСТЬNULL(НомераМНО.Номер, "") <> ""
                 ТОГДА ", подтверждение " + НомераМНО.Номер
             ИНАЧЕ ""
         КОНЕЦ КАК МНО

       + дополнительные колонки:
         ДатаДоговора       (тип Дата)
         ДатаПодтверждения  (тип Дата, = МНО.Дата)

  Вид сделки
    -> ВЫБОР Приход ТОГДА "Размещение" ИНАЧЕ "Закрытие"
       (стр. 2000-2004).

  Валюта
    -> ДенежныеСредстваМНО.МНО.РасчетныйСчет.Валюта  (стр. 2008).

  Сумма в валюте
    -> ДенежныеСредстваМНО.Сумма  (стр. 2005).

  Ставка
    -> ДенежныеСредстваМНО.МНО.Процент  (стр. 2007).

  Срок (дней)
    -> РАЗНОСТЬДАТ(МНО.Дата, МНО.ДатаВозврата, ДЕНЬ)  (стр. 2009).

  Банк (4 ячейки merge)
    -> ЕСТЬNULL(РеквизитыБанка.КраткоеНаименованиеПоУставу,
                ПРЕДСТАВЛЕНИЕ(МНО.РасчетныйСчет.Банк))
       Срез РеквизитыЮридическихЛиц по
       МНО.РасчетныйСчет.Банк.ЮрФизЛицо  (стр. 2010, 2017).

ИСКЛЮЧЕНИЕ СТОРНИРОВАННЫХ МНО:
  Сохранено левое соединение с Документ.СторнированиеМНО и WHERE-

  оригинального модуля.

6. ВТ "ДепозитныеВклады"
================================================================================

Источник: РегистрНакопления.ДенежныеСредстваВКредитныхИнструментах
          + РегистрСведений.УсловияКредитныхИнструментов.СрезПоследних.
  Базовый текст: ВывестиСделкиДепозитнымВкладам (стр. 1913-1992).

Сначала формируется промежуточная ВТ "_ТаблицаДвиженийДепо" (аналог
_ТаблицаДвижений из стр. 1926-1943), затем финальная ВТ.

Соответствие колонок XML:

  Наименование клиента, Номер договора ДУ
    -> Аналогично МНО (срез РеквизитыЮридическихЛиц по Клиенту).

  Дата операции
    -> ДенежныеСредстваВКредитныхИнструментах.Период  (стр. 1918).

  Депозитный вклад (4 ячейки merge)
    -> ДенежныеСредстваВКредитныхИнструментах.КредитныйИнструмент
       (Справочник.ДепозитныеВклады)  (стр. 1919).

  Вид сделки
    -> ВЫБОР Приход ТОГДА "Размещение" ИНАЧЕ "Закрытие"  (стр. 1920-1924).

  Валюта
    -> ДепозитныйВклад.БанковскийСчет.Валюта  (стр. 1952).

  Сумма в валюте
    -> ДенежныеСредстваВКредитныхИнструментах.Сумма  (стр. 1925).

  Ставка
    -> УсловияКредитныхИнструментов.Процент  (стр. 1953).

  Срок (дней)
    -> РАЗНОСТЬДАТ(ДепозитныйВклад.ДатаРегистрации,
                    УсловияКредитныхИнструментов.ДатаПогашения, ДЕНЬ)
       (стр. 1954).

  Банк (4 ячейки merge)
    -> ЕСТЬNULL(РеквизитыБанка.КраткоеНаименованиеПоУставу,
                ПРЕДСТАВЛЕНИЕ(ДепозитныйВклад.БанковскийСчет.Банк))
       Срез РеквизитыЮридическихЛиц по
       ДепозитныйВклад.БанковскийСчет.Банк.ЮрФизЛицо  (стр. 1955, 1975).

ВЫБОР ПРАВИЛЬНОГО УСЛОВИЯ ПО ДАТЕ ОПЕРАЦИИ:
  Подзапрос "ВЫБРАТЬ ПЕРВЫЕ 1 ... УПОРЯДОЧИТЬ ПО ДатаНачалаДействияУсловий
  УБЫВ" - точная копия стр. 1960-1970 из модуля: для каждой строки
  движения мы выбираем последнюю действующую запись условий, у
  которой ДатаНачалаДействияУсловий <= ДатаОперации.

ФИЛЬТР ТИПА ИНСТРУМЕНТА:
  ТипКредитногоИнструмента = ДепозитныйВклад  (стр. 1938).

7. ВТ "ИтоговаяТаблица" - ШИРОКОЕ ОБЪЕДИНЕНИЕ
================================================================================

Это виртуальная "плоская" таблица, объединяющая все 4 ВТ через
ОБЪЕДИНИТЬ ВСЕ. Каждый раздел даёт свою группу строк.

КОЛОНКА-МАРКЕР "ТипОперации":
  "1. Сделка"          - из ВТ Сделки
  "2. Сделка РЕПО"     - из ВТ СделкиРЕПО
  "3. МНО"             - из ВТ МНО
  "4. Депозитный вклад"- из ВТ ДепозитныеВклады

Префикс "1.", "2." и т.д. сохраняет естественный порядок при
сортировке по этой колонке.

СТРУКТУРА КОЛОНОК (32 колонки):
  ОБЩИЕ (для всех 4-х):
    ТипОперации
    НаименованиеКлиента
    НомерДоговораДУ
    Дата
    ВидСделки
    Валюта         (для Сделок - ВалютаСделки; для РЕПО - ВалютаСделки;
                    для МНО/Депо - валюта счёта)
    Сумма          (для Сделок - СуммаСделкиСНКД; для РЕПО - Сумма1ЧастиСНКД;
                    для МНО/Депо - СуммаВВалюте)

  ДЛЯ СДЕЛОК / РЕПО (NULL для МНО, Депо):
    НаименованиеЭмитента, НомерГосРегИлиISIN, ВидЦеннойБумаги,
    МестоЗаключения, Количество, ВалютаНоминала, Номинал,
    ЦенаОднойЦБ        (= ЦенаОднойЦБ1 для РЕПО),
    НКДОднойЦБ         (= НКДОднойЦБ1 для РЕПО),
    ВалютаРасчетов,
    ДатаОплаты         (= ДатаОплаты1Части для РЕПО),
    ДатаПереходаПравНаЦБ (= ДатаПереходаПрав1Части для РЕПО),
    КомиссииБиржи, КомиссииБрокера

  ТОЛЬКО ДЛЯ РЕПО (NULL для остальных):
    СтавкаРЕПО, ЦенаОднойЦБ2, НКДОднойЦБ2, Сумма2ЧастиСНКД,
    ДатаОплаты2Части, ДатаПеререгистрации2Части, СделкаИлиИзменение

  ДЛЯ МНО / ДЕПОЗИТОВ (NULL для остальных):
    МНОИлиВклад   (Документ.МНО ИЛИ Справочник.ДепозитныеВклады)
    Ставка
    СрокДней
    Банк

Порядок и имена колонок строго одинаковые во всех 4-х частях
ОБЪЕДИНИТЬ ВСЕ - это обязательное требование 1С: при объединении
типы колонок определяются по первому "не-NULL" значению среди
всех arm-ов.

================================================================================
9. ДОПУЩЕНИЯ И ОТСТУПЛЕНИЯ ОТ МОДУЛЯ 482
================================================================================

(а) Курсы валют НЕ пересчитываются.
    В модуле есть ВТ _КурсыВалют и для сделок считается
    "СуммаВсегоВВалютеОплаты" (стр. 1319) и для РЕПО -
    "СуммаВсего1ВВалютеОплаты" / "СуммаВсего2ВВалютеОплаты"
    (стр. 1624, 1638). В XML примере соответствующих колонок нет,
    поэтому курсовый блок исключён - запрос проще, читать в консоли
    удобнее.

(б) Поля "СуммаКупона", "ЦенаКупона" доступны только для облигаций.
    Для прочих типов ЦБ возвращается NULL (как в модуле, стр. 1310-1312,
    1614-1617, 1629-1631).

(в) Колонка "Дата" по сделкам - это УсловияСделок.Период (по сути -
    отметка регистра сведений). Если потребуется именно "ВремяСделки"
    из документа, это поле есть в модуле (стр. 1294-1300) - можно
    добавить отдельной колонкой.

(г) В качестве "Наименование эмитента" для паёв используется
    "ПаевойИнвестиционныйФонд" (название фонда), а не "Управляющая
    компания". Это эквивалентно описанию из модуля
    "ОписаниеФинВложения" (стр. 2913, 2968 и др.) где для паёв
    действительно выводится наименование фонда.

(д) Внутренние ВТ каскада РЕПО (_РЕПО_*) уничтожаются перед
    финальными SELECT-ами - они не нужны в результате. Точно так же
    уничтожается _ТаблицаДвиженийДепо.

(е) Поля "Сделка" и "Регистратор" - оставлены в выходных ВТ
    Сделки, СделкиРЕПО, МНО, ДепозитныеВклады как служебные ссылки на
    исходный документ - удобно для проверки данных. В ИтоговуюТаблицу
    они не включены.

10. ИСПОЛЬЗОВАНИЕ В КОНСОЛИ
================================================================================

Шаги:
  1. Открыть консоль запросов (типовой "Консоль запросов" или
     встроенная в конфигурацию).
  2. Скопировать содержимое "Запрос_Науфор.txt" целиком.
  3. Заполнить параметры:
        Организация    - своя организация (например, "Организация_РПИ").
        НачалоПериода  - 01.01.2025 00:00:00
        КонецПериода   - 31.03.2025 23:59:59
        СписокКлиентов - массив ЮрФизЛиц (через панель Параметры -
                          добавить тип Массив, в нём строки -
                          Справочник.ЮрФизЛица).
        СписокСчетовДУ - либо пустой массив, либо массив счетов ДУ.
  4. Выполнить.

Если ни СписокКлиентов, ни СписокСчетовДУ не заполнены - запрос
вернёт пустые таблицы (это страховка).
