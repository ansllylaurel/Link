## 5. Diff кода old (2.29) → new (2.31)

### 5.1. Модуль объекта

Только это (плюс версия 2.29 → 2.31):

1. После успешного `ПолучитьПараметрыШапки`:
   ```
   ЭтотОбъект.СчетДоверительногоУправления = ПараметрыШапки.СчетДоверительногоУправления;
   ```
2. В СКД передаётся параметр `СчетДоверительногоУправления`.
3. В запросе `ПолучитьПараметрыШапки` к срезу `КлиентыДоверительногоУправления` добавлено:
   - ветка: если счёт ДУ пустой — фильтр по ПИФ, иначе по счёту;
   - `ДатаРасторжения` пустая **или** `>= &Период`.

`ПолучитьСЧАНаДату` по-прежнему берёт `ЭтотОбъект.СчетДоверительногоУправления`.  
После формирования сравниваются: СЧА из макета vs регистр `ФинансовыеПоказатели`; СЧА рынка vs балансовая колонка макета. Расхождение — **сообщения пользователю**, отчёт не стопается.

Старый код **не** копировал счёт из шапки. Если на форме выбран только ПИФ, `СчетДоверительногоУправления` может остаться пустым: `ПроверитьРегистрациюСЧА` идёт по счёту из шапки, а `ПолучитьСЧАНаДату` — по пустому реквизиту → 0.

На форме `ОпределитьКаталогВыгрузки` вызывается из `ПериодПриИзменении` и `СчетДоверительногоУправленияПриИзменении`, **не** из выбора ПИФ. При смене счёта реквизит сначала **очищается** (`Отчет.СчетДоверительногоУправления = ""`).

`ПолучитьПараметрыШапки` при нескольких строках делает `Выборка.Следующий()` — берёт **первую** строку без правила «действующий счёт».

### 5.2. СКД `_СчетаДУ`

**Old:** клиент = ПИФ **и** организация счёта = `&Организация`. Без даты расторжения, без параметра счёта ДУ.

**New:** как в шапке объекта: ПИФ **или** конкретный счёт; плюс `ДатаРасторжения`; параметр `СчетДоверительногоУправления` добавлен в схему.

### 5.3. СКД — МНО (бэк)

New в выборе субъекта для дебиторки:

```
ТИПЗНАЧЕНИЯ(СубъектАналитики) В (ТИП(Документ.МНО), ТИП(Документ.СделкаСМО))
ИЛИ ТИПЗНАЧЕНИЯ(Основание) В (ТИП(Документ.МНО), ТИП(Документ.СделкаСМО))
```

Потом `ВЫБОР`: если тип субъекта МНО/СМО — субъект, иначе **Основание**.

**Это нелегально:** `Основание` = `DefinedType.ОснованиеСтоимостиАктивов`, в составе **нет** `Документ.МНО` и **нет** `Документ.СделкаСМО`. В консоли запросов это даёт ошибку. Тот же конструкт нельзя оставлять в СКД.

`СубъектАналитики` = `СубъектыАналитики` — МНО и СделкаСМО **есть**. Сравнивать МНО можно только с субъектом.

### 5.4. СКД — МНО (БУ)

Old: признак `% по МНО` если `ТИПЗНАЧЕНИЯ(ВидАктива) В (Документ.МНО, СделкаСМО)`.

New: ещё `УчетныйАктив В (ПроцентыНаМНО, ПроцентыНаСМО, ПроцентыНаФЕО)` **или** тип вида актива МНО/СМО. Плюс подпись `"% по счету " + БанковскийСчет`.

На 12.03 в запросе 5 `УчетныйАктив` из настроек **не сросся** (NULL). Подтверждения, что эта ветка чинит п.2 задания, нет.

### 5.5. СКД — отрицательные БУ-остатки

New ужесточает `ГДЕ` у `_ОстаткиАктивовНаСчетахУчетаБУ` (не вся минусовая кредиторка попадает в перечень). **Запросами не проверялось.** На п.1 задания (передача Траст) по суммам счетов ДУ не опирается.

## 8. Выводы (обязательны для следующего агента)

### 8.1. Почему «нет расхождения» — не из‑за смешения счетов в цифрах

Передача чистая: до даты расторжения данные на старом, после — на новом, второго хвоста в регистрах рынка/СЧА/сырого БУ **нет** (12.03 и 31.03).  
`ДатаРасторжения` в `_СчетаДУ` **не объясняет** изменение итогов бэк vs баланс.

Её можно оставить как **гигиену** (два одноимённых счёта, оба РЕГИОН ЭсМ, не ждать нулей навсегда). Нельзя называть её фиксом п.1 задания по суммам.

На 12.03 она ещё и **не отсекает** Академию (расторжение 13.03).

### 8.2. Наиболее правдоподобная причина пользовательского «расхождения»

Сообщения после компоновки: СЧА макета ≠ СЧА регистра; рынок ≠ баланс макета.

Старый `ПолучитьСЧАНаДату` при пустом `ЭтотОбъект.СчетДоверительногоУправления` (выбран только ПИФ) сравнивает ненулевой СЧА отчёта (СКД по ПИФ собрала все счета, фактически один живой) с **0** в регистре.

Новый код записывает счёт из шапки в объект и отдаёт его в СКД — сверка идёт по конкретному счёту.

Это **не проверено повторным прогоном отчёта** (нет лога сообщений). По коду и данным счетов — лучшая гипотеза. Имеет смысл оставить и сделать однозначный выбор действующего счёта (`ДатаРасторжения` max / пустая), а не `Следующий()`.
